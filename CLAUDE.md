## Code style
- Don't write comments that restate what the code already says.
- Comment only the "why" when something isn't obvious: workarounds,
  counterintuitive decisions, constraints from an external API.
- No section-divider comments like `// --- Helpers ---`.
- Don't leave comments describing the change you just made.

## Ports and certificates

Порт 80 на серверах не открываем никогда. Сертификаты обновляются только через порт 443 (tlsChallenge). Не добавлять httpChallenge и публикацию порта 80 ни в код, ни в установщик.

## Builds

Build commands in `services/application.ts` and `services/compose.ts` go through `createBuildRunner` (`packages/server/src/utils/process/build-process.ts`), not `execAsyncRemote` directly. It adds the time budget (`buildTimeoutMinutes` on `server` and `webServerSettings`, default 60), `timeout` on the server that builds, so a build stops there even after the panel lost the connection, and the `dokploy-build:<appName>` marker that Kill Build and the next build of the service use to find its processes. `recordBuildFailure` in the same file writes the failure to the log and never stops the status update when that server is out of reach. Every ssh2 connection a deployment waits on takes `SSH_KEEPALIVE`.

## Database deployments

`waitForSwarmServiceConvergence` (`packages/server/src/utils/docker/utils.ts`) decides whether a database deployment succeeded. `service.update` clears `UpdateStatus`, so the state it reads belongs to this update, and Swarm sets `updating` about 50 ms later only if a task has to change. A fresh service, an update with nothing to roll out and a scale change never get a state, and until the update starts the running task is the old one, so a missing state counts only after 2 s and only when no running task has another `ForceUpdate`. Task specs cannot be compared with the service spec as a whole: `Runtime` exists only on the service, and a placement change alone rolls nothing out. `rollback_started`, `rollback_completed`, `rollback_paused` and `paused` fail at first sight, because Swarm can replace `rollback_completed` with `completed` seconds later and reports it before the old task is up. `completed` also needs enough running tasks, because `FailureAction: continue` completes with its tasks restarting. Five builders bump `ForceUpdate`, so their every deploy replaces the task and waits at least `UpdateConfig.Monitor`, 5 s by default; `buildLibsql` does not. `getSwarmConvergenceTimeoutMs` scales the limit with the batches, the stop grace period, a health check, Monitor and Delay; the default spec comes to 45 s. Swarm watches a task for `Monitor` only during an update, and a restart loop shows a running task on some polls, so a task counts only once the same task ID has stayed up for `Monitor`. A restart always makes a new task, so the ID tells. Time counts from the panel's first sight of the task, on the panel's clock and only as a difference, plus what the cluster shows from before the service's last change: `UpdatedAt` minus the task's `Status.Timestamp`, used only when the task's `Version.Index` is older than the service's, which rules out a node with a slow clock making a new task look old. So a redeploy that changes nothing still takes 2 s and a `completed` update adds no wait. A fresh service (first deploy, Rebuild, transfer) or a new replica waits for the task and then `Monitor`, 8 to 10 s by default. One that fails once and recovers passes, because a first crash can be transient. One in a restart loop fails at the limit, 45 s by default, and so does a `FailureAction: continue` update whose tasks keep restarting. A crash later than `Monitor` goes unseen, as it does for Swarm. A read that fails or gets no answer in 30 s is tried again until the limit, because the update goes on without the panel. `SSH_KEEPALIVE` sees a dead network, not a daemon that took the request and stays silent, and such a read used to hold the deployment's slot in the queue for good. The limit is checked between reads, so a silent daemon can overrun it by up to one read. `swarm-convergence.real.test.ts` runs this on real Docker.

## Deployment logs

A deployment's log stays where it was written. Reads and single removals find that place through `getDeploymentLogServerId` (`packages/server/src/utils/deployments/log-server.ts`): the row's build server, otherwise the owning service's server, otherwise the panel. `deployment.serverId` is the exception: it marks a server's setup or hardening run, whose log the panel keeps on its own disk, so nothing connects to that server for it and `getAccessibleServerIds` is the only organization check on reading it. Deleting an application cascades to its deployment rows before `removeDeployments` runs, so past build servers come from the rows loaded with the application. `removeDeployment` keeps the row when the log could not be removed, so the removal can be repeated. The rotation of old deployments drops the row anyway and opens one connection per server, so a dead server neither stops a new deployment nor delays later ones again.

## libSQL replicas

`buildLibsql` runs its own command through `/bin/sh -c` in place of the image's entrypoint, and only that entrypoint turns `SQLD_PRIMARY_URL` into `--primary-grpc-url`. `sqld` itself reads `SQLD_PRIMARY_GRPC_URL`, so the panel sets that in Env: the free-text URL stays out of the shell, and a custom `sqld` command replicates too, with its own `--primary-grpc-url` taking precedence. `SQLD_PRIMARY_URL` stays for custom commands that refer to it. `sqld` refuses `--grpc-listen-addr` together with a primary URL, so a replica's command has none, and `buildLibsql` rejects a custom command that has it: Swarm would roll that update back while `waitForSwarmServiceConvergence` had already reported success. The URL takes the primary's gRPC port, 5001. With a wrong host or port the replica keeps running, its requests hang, and its log says `error connecting to primary`. `https://` fails the same way without the `--primary-grpc-tls` flags, and a URL without a scheme makes `sqld` panic on every request while it stays up. `getLibsqlPrimaryUrlProblem` (`libsql-primary-url.ts`, free of server-only modules) rejects both and an empty URL, for `buildLibsql` and for the replica's form.

The form is `ShowLibsqlPrimaryUrl`, and it saves through `libsql.update`, so its permission check is that procedure's. A saved URL reaches the node on the next deploy; Reload keeps the old spec. The URL can hold a password, so `redactDatabaseServiceSecretsFor` hides that part on every read, and the host stays readable. A URL that comes back as shown keeps the stored password. An edited one is saved as sent, placeholder included, so a stored password never travels to a host the caller picked, for the reason in `assertStoredSecretTargetUnchanged`. `apiUpdateLibsql` redefines `enableNamespaces` and `dockerImage` without defaults, because `.partial()` keeps a zod default: every update used to turn namespaces off for the next deploy. Nothing in the panel turns them back on after creation, only the same API.

A command of `""` or only spaces means no override, as null does, so it runs the default command. The custom command form saves `""` whenever it is saved with an empty field, even if only the image changed. Without namespaces `""` used to run the image's entrypoint, which opens no admin port and runs `sqld` as the user `sqld`; with them, `/bin/sh -c " --enable-namespaces"` exited with 127. A service that ran the entrypoint moves to the default command on its next deploy and keeps its data, and a replica keeps replicating with nothing set aside, but `SQLD_DB_PATH` and the `SQLD_*_LISTEN_ADDR` names in its env lose to the default command's flags.

Nodes pick a namespace by the first label of `Host`. A replica needs `--enable-namespaces` to serve named namespaces; without it, it follows only the primary's default one.

`sqld` connects to the primary on the first request, not at start, and if it finds data without `client_wal_index` it overwrites that with the primary's, with no warning. Replicas used to run as primaries of their own, so the default command moves such an `iku.db` to `iku.db.before-replica-<unix time>` once, in the same volume, and nothing deletes the copy. A custom command gets no such step. `--db-path` stays `iku.db` because the panel's backup form fixes that name. `libsql-replica.real.test.ts` runs all of this on real Docker; after a new image, it is what shows whether that file layout still holds.

## Redis start

`buildRedis` starts a database with `REDIS_START_SCRIPT`, which reads the password from `DOKPLOY_DB_PASSWORD` in Env, so the shell never parses it. `REDIS_PASSWORD` stays in Env for the container, but the service env can set that name and dotenv changes some values, so nothing starts from it. `exec` makes `redis-server` PID 1: with `/bin/sh -c` alone, dash in the Debian image stays PID 1 and never passes SIGTERM on, so a stop ends in SIGKILL with no final save. `command: ""` and `args: []` are what the custom command form saves when left empty, and they count as no override. An empty password stops the start, because Redis takes it as no password. Redis 6 reads a password that starts with `--` as an option name; 7 and up do not. `redis-password.real.test.ts` runs this on real Docker, including the old command as the starting point.

The panel's password change (`changeRedisPassword`, `utils/databases/redis-password.ts`) writes `DOKPLOY_DB_PASSWORD` and `REDIS_PASSWORD` into the service spec, because Swarm restarts a task from the spec and `CONFIG SET requirepass` lives in memory. Swarm cannot change a spec without replacing the task, so every change is a restart: clients drop for about half a second on a small database, Redis makes its final save on SIGTERM, and old connections end, which `CONFIG SET` left alive. Nothing else in the spec moves, so env edits and an image that wait for a deploy still wait. Nothing goes to Redis first, so a failed update leaves everything as it was and the row's transaction rolls back. The mutation waits for `UpdateStatus` and fails only on `rollback_*`, since Swarm then went back to the old spec; past the 90 s deadline the new spec stands, so the row follows it. `redis-cli` exits with 0 when Redis refuses, so only the reply counts. A database still on the old command gets `SAVE` first, because its stop ends in SIGKILL: the row's password, then the one in the old command's text. Writes in the 10 s between that save and the kill are lost, once. A custom command decides what a restart brings back, and restarting could undo the change at once, so it gets only `CONFIG SET`, and the dialog says so. A stopped database changes only in the spec and needs no container.

## Service updates

The application, database and rollback builders write a service through `createOrUpdateSwarmService` (`utils/docker/swarm-service.ts`). Only a 404 leads to a create. Each of them used to create on any error, so a refused update reached the user as `name conflicts`. Each call has 30 s, and one that gets no answer is not repeated, because the daemon may still apply it. The `abortSignal` can go into the options: `docker-modem` removes it before it builds the query and the body. `__test__/docker/swarm-service.test.ts` runs against a real HTTP server through dockerode, and fails if an upstream merge brings `docker.createService(` back to these eight files. `redis-password.ts`, the setup code and the terminal or log reads have calls of their own without this limit.

## Application deployments

All four deploy paths in `services/application.ts` end in `rollOutApplication`: `mechanizeDockerContainer`, then `waitForApplicationRollout` (`utils/builders/index.ts`), which is `waitForSwarmServiceConvergence` with an option the databases do not use. The wait reads the service on `application.serverId`, while the log lines stay on the server that built the image. A pull on the node that runs the task and a HEALTHCHECK of the image itself show in no spec, so `quietStartAllowanceMs` gives a task that reports no error 10 more minutes per batch; a fixed 45 s would fail healthy deployments. As soon as a task carries an error (a crash, `no suitable node`), the limit of the spec, 45 s by default, runs from that moment, because Swarm restarts a fresh service's task forever and leaves a stuck update in `updating`, and only this ends them. A start-first update of a service with a host-mode port cannot start on one node: Swarm stays in `updating` with `host-mode port already in use`, so this now fails instead of reporting success. Job modes never get here, because Docker refuses a job with `UpdateConfig` and `generateConfigContainer` always sends one. `reload` in the router and the panel's Rollback (`services/rollbacks.ts`) update the service and do not wait. Neither does compose: `docker stack deploy --detach=false` exits 0 with `converged` after a rollback, so a stack needs one wait per service found through `com.docker.stack.namespace`, without its job services, and the `docker-compose` type has no Swarm at all. `application-rollout.real.test.ts` runs this on real Docker.

## Mongo replica sets

`replicaSets: true` replaces the image entrypoint with the script in `packages/server/src/utils/databases/mongo.ts`, so `MONGO_INITDB_ROOT_*` do nothing there and the script itself runs `mongod --auth --keyFile`. The key file is generated at `/data/db/.dokploy-keyfile`, in the data volume, so it goes with the data through a volume backup or a rebuild. Credentials reach the script through `DOKPLOY_DB_USER` and `DOKPLOY_DB_PASSWORD` in Env, never through its text. Data without a key file gets one more start without access control on the next deploy, which makes the stored user and password valid, and then restarts with it; nothing changes for a running database until that deploy. `mongo-replica-set-auth.real.test.ts` runs all of this on real Docker, including the old script as the starting point. It uses `mongo:7`: `mongod` 8 refuses to start on kernels from 6.19 up to 7.0.13 (SERVER-121912), and GitHub-hosted runners have 7.0.0.

The connection strings the panel shows come from `apps/dokploy/lib/mongo-connection-url.ts`. The external one always carries `directConnection=true`: a replica set names its member `<appName>:27017`, which resolves only inside the Docker network, so a driver outside that follows discovery cannot connect. The internal one leaves discovery on for a replica set. `mongosh` adds `directConnection=true` to a one-host URL that does not set it, so a check through `mongosh` sees what a driver does only with an explicit `directConnection=false`.

## Mongo tool arguments

`getMongoBackupCommand`, `getMongoRestoreCommand` and `buildMongoPasswordChangeCommand` pass `--username=<user>` and `--password="$DOKPLOY_DB_PASSWORD"`, with the password in `docker exec -e`. The password validator allows a leading `-`, and the `-p <value>` form fails on it however well the shell quotes it: `mongodump` and `mongorestore` refuse `-x` and `--port` before connecting, and `mongosh` also refuses a lone `-`. The text of a failed command reaches the UI, and an env assignment is what `redactSensitiveText` masks whole. `__test__/backups/mongo-password-argument.test.ts` fails if an upstream merge puts the old form back.

## Database connection strings

The strings the panel shows for Postgres, MySQL, MariaDB, Redis and libSQL come from `apps/dokploy/lib/database-connection-url.ts`, and Mongo's builders use its `encodeCredentials` and `formatUrlHost`. The user, the password and the database name are percent-encoded, because `DATABASE_PASSWORD_REGEX` allows `@ : ? # %` and no validator limits the name. A host with a colon gets brackets, because `getPublicIpWithFallback` falls back to IPv6 and `server.ipAddress` accepts any text. Two clients fail on such a string for reasons of their own: `@libsql/client` refuses any URL with credentials, and `node-redis` looks up the address with its brackets.

## Sidebar links

`next/link` prefetches the page of every link in the viewport and then runs that page's module on idle, also from the browser cache, so the sidebar made each dashboard load fetch and execute 17 pages nobody had opened. Its links and the breadcrumb's plain link take `prefetch={false}`, which still loads a page when the pointer or a finger reaches the link. On a slow link this makes the first click on a page slower, once per page per panel build; a normal desktop does not notice. Links inside a page keep prefetching, because they are likely next clicks. `sidebar-no-prefetch.test.ts` fails if an upstream merge drops the prop.

## Websocket handlers

Every server in `apps/dokploy/server/wss/` registers through `onWebSocketConnection` (`onJsonWebSocketConnection` for a client that parses every message as JSON) and reads the path with `readUpgradePathname`, both in `server/wss/connection.ts`. The fork has no process-level listeners of its own: only Next's, installed by `app.prepare()`, keep the panel alive after an exception from a handler, an `upgrade` listener or the HTTP listener in `server.ts`, and they only log it, leaving the socket open with nothing on it. The wrapper logs the failure, tells the client and closes with 1011. Its text is generic because the session check runs first, so the error could reach a client that has not signed in. It also adds the `error` listener, since `ws` emits a malformed frame as `error` and an emitter with no listener throws. `ws.close()` throws on a reason over 123 bytes, so a reason built from an error goes through `toCloseReason`.

`closeUnknownUpgradePaths`, the last listener `server.ts` adds, answers 404 and closes an upgrade to a path no server handles. Nothing reads such a socket and Node has dropped its timeouts by then, so it would stay in `CLOSE_WAIT` until a restart, even after the client left. Next closes only paths that match a page and leaves the rest on purpose, since an application's own server may listen there. The paths have no list to keep in step: the two helpers record `wss.options.path` when a server registers, so a server that was not set up, like the stats one in the cloud, counts as unknown. In dev everything under `/_next/` stays open for Next's own listener. Its hot reload socket is `/_next/hmr` in Next 16.4, so the `/_next/webpack-hmr` check each listener keeps from upstream matches nothing. Node passes any `Upgrade` header to these listeners, so `curl --http2` over plain HTTP gets this 404 too. `__test__/wss/handler-errors.test.ts` fails if an upstream merge brings back a plain `wss.on("connection")` or `new URL` in an `upgrade` listener, or adds a server without a `path`, outside `server/wss/` or missing from the list its socket tests run on.

## Panel backup notifications

`dokployBackup` turns on messages about the panel's own backup, and `dokployBackupErrorsOnly` then leaves out the successes, because that backup can run every hour and a channel with a message per run gets muted, or the event stays off and a failure goes unseen. The setting stays out of `.pick()` in the provider schemas and comes after `.required()`, so an API client that does not know it can still create a channel. A backup that never starts sends nothing, in either mode. `__test__/notification/dokploy-backup-errors-only.test.ts` checks the sending, every provider's schema, and that the service and the form carry the setting for every provider.

## Pull requests

Every pull request targets `AgentHits-Dev`, including a PR that builds on another open PR. Checks run only for that base, so a PR stacked on another branch gets none. When one PR depends on another, say so in the description; do not change the base.

## Releases

One GitHub release `agenthits-vX.Y.Z` covers a batch of work, not a single PR (owner's decision 2026-10-27). Every push to `AgentHits-Dev` builds the image through `.github/workflows/agenthits-release.yml` (`agenthits-dev`, `agenthits-dev-<sha12>`), and panels show such a build as `agenthits-vX.Y.Z-N-g<sha12>`: the previous release plus N commits. A push cuts the release once 20 PRs (`RELEASE_EVERY`, first-parent commits) have been merged since the previous release; to release a finished batch sooner, run `gh workflow run agenthits-release.yml --repo TaskFlow-Systems/dokploy --ref AgentHits-Dev`. Several PRs that belong together can also be merged as one combined PR. The `agenthits-` prefix keeps fork tags apart from upstream Dokploy `v0.x` tags. The version goes up by patch, by minor when a PR title in the batch starts with `feat`, and by major only through a manual run with `bump: major`. The release notes are the title and body of every PR merged since the previous release, so write each PR description for someone reading the release. The image of a release is `ghcr.io/agenthits/dokploy:agenthits-vX.Y.Z` and panels show that tag as the fork version; `agenthits-dev` always points at the newest build. After the GitHub release is published, `.github/workflows/agenthits-stable-tag.yml` points `agenthits-stable` at the release's manifest (same digest, no rebuild); the panel's Update follows `agenthits-stable` and never offers a release older than the running build. A manual run of that workflow with an older release moves the channel back; `DOKPLOY_AGENTHITS_UPDATE_TAG=agenthits-dev` on a panel's service makes it follow every build. `install-agenthits.sh` and `update.sh` still default to `agenthits-dev`. `.github/workflows/agenthits-ghcr-retention.yml` deletes old GHCR versions weekly but never a release tag, `agenthits-dev`, `agenthits-stable` or `buildcache`.

## Dependencies

`.github/workflows/deps-auto-update.yml` runs every day at 03:00 UTC (manually: `gh workflow run deps-auto-update.yml --repo TaskFlow-Systems/dokploy --ref AgentHits-Dev`). It runs `bun update --recursive` within the `package.json` ranges (minor and patch, direct and transitive packages, versions at least one day old), then `bun audit`, and keeps one PR `зависимости: автообновление библиотек` from `deps/auto-update` into `AgentHits-Dev`, rebuilt daily until it is merged. It starts `pull-request.yml` and `bun-migration-docker-check.yml` on the branch through `workflow_dispatch`; judge the PR by those runs. It never merges. The same workflow runs in the owner's other projects; it replaced Dependabot for Bun, which moves only direct dependencies. It needs "Allow GitHub Actions to create and approve pull requests" in the repo's Actions settings.

- Held packages stay pinned to exact versions (`better-auth`, `@better-auth/*`, `auth` (the `better-auth` CLI), `better-call`, `@better-fetch/fetch`, `stripe`, `@stepperize/react`, `@dokploy/trpc-openapi`) or `~` (`ssh2`), in their `package.json` and in the root `overrides`, so the workflow does not move them. Keep new holds pinned the same way.
- `@biomejs/biome` stays exact too: a new version can change formatting and lint results, so it moves by hand.
- `node-pty` takes a `^` range, but only one job guards it: it has no Linux prebuild, so the image compiles it, and the tests mock it. `main-image-smoke` in `bun-migration-docker-check.yml` loads it in the built image and runs a command through it, so a daily PR that moves it waits for that job. The job does not cover `docker exec` behind the panel's websocket; after such a merge, open a container terminal on a running panel.
- `node-gyp` in `Dockerfile`, `Dockerfile.server`, `Dockerfile.schedule` and `Dockerfile.cloud` stays exact and moves by hand: `bun install --production` skips the root devDependency, so this global install compiles `node-pty` and the other native packages for the image, and no workflow moves it. Keep all four at the version `bun.lock` holds for the root `node-gyp`: when the daily update moves it there, raise them in a separate PR and judge it by `main-image-smoke`.
- `sharp` and `@img/*` stay in `bun.lock` because `sharp` is an optional dependency of `next`. `images.unoptimized` in `next.config.mjs` turns off `/_next/image`, the only code that loads it, and the `prod-deps` stage of `Dockerfile` deletes both directories; `main-image-smoke` checks they are gone.
- `apps/schedules` declares no `ioredis` of its own: the queues pass `connection` as plain options, and `bullmq` brings `ioredis` as an exact version. A direct `ioredis` at any other version leaves two copies in the lockfile.
- `inngest` stays at 4.26.1: 4.26.2 ships `sandbox-tool/dist/inngest-tool-linux-amd64`, built with Go 1.22, and the image scan fails on its Go stdlib findings. Move it when a release drops that binary or builds it with a current Go; do not add these findings to `.trivyignore.yaml`.
- Everything else takes a `^` range in every `package.json` that declares it, so the daily update moves it. A new exact version needs a line here saying why. On `0.x`, `^` narrows to patch (`^0.12.0` is `<0.13.0`), so a minor of `@xterm/addon-*`, `drizzle-zod` or another `0.x` package moves by hand.
- Every other root override is a range `>=<fixed version> <next major>` (for `0.x`, `<next minor>`), so the override keeps the fixed floor and the workflow still moves the package. A security override follows the same form; an exact version there freezes the package and can silently override a newer direct dependency.
- A package that `packages/server` and an app both declare takes the same range in both (`@trpc/server`, `undici`). With an exact version on one side and a range on the other, the daily update moves only the range and the lockfile keeps two copies; `instanceof` across them then fails, as a `TRPCError` thrown in `packages/server` did in the router tests.
- Major updates are done by hand, one PR each (the `dokploy-upgrader` agent), with `bun add <pkg>@<ver> --minimum-release-age=86400`.
- The one-day age is `minimumReleaseAge` in `bunfig.toml` and `MIN_RELEASE_AGE` in the workflow; change both together.
- A commit pushed to the branch of the open PR stops its daily rebuild until the PR is merged or closed.
- `.github/workflows/dependency-audit.yml` runs `bun audit` every Monday for advisories published between updates.
- `bun audit` does not see the image. Trivy scans the published `agenthits-dev` image and the pinned Traefik, Postgres and Redis images every Monday (`.github/workflows/image-audit.yml`), each `agenthits-dev-<sha12>` build once the release workflow has pushed it (same workflow), and the image a PR builds (`bun-migration-docker-check.yml`). All of them run `.github/scripts/trivy-image-scan.sh`, which writes the findings to the job summary, and fail on critical and high findings that have a fix in Debian packages, in the Go binaries of the bundled tools (Docker CLI, rclone, Railpack, pack) or in npm packages inside the image. `.trivyignore.yaml` holds findings whose latest tool release still carries them; each entry expires, so the audit fails again and the tool gets rechecked. Trivy is pinned by digest in both workflows; move them together. The organization's self-hosted Linux runners take no public repositories, so these scans run on GitHub-hosted runners.
