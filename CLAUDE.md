## Code style

- Don't write comments that restate what the code already says.
- Comment only the "why" when something isn't obvious: workarounds,
  counterintuitive decisions, constraints from an external API.
- No section-divider comments like `// --- Helpers ---`.
- Don't leave comments describing the change you just made.

## Ports and certificates

Порт 80 на серверах не открываем никогда. Сертификаты обновляются только через порт 443 (tlsChallenge). Не добавлять httpChallenge и публикацию порта 80 ни в код, ни в установщик.

## Builds

Build commands in `services/application.ts` and `services/compose.ts` go through `createBuildRunner` (`packages/server/src/utils/process/build-process.ts`), not `execAsyncRemote` directly. It adds the time budget (`buildTimeoutMinutes` on `server` and `webServerSettings`, default 60), `timeout` on the server that builds, so a build stops there even after the panel lost the connection, and the `dokploy-build:<appName>` marker that Kill Build and the next build of the service use to find its processes. `recordBuildFailure` in the same file writes the failure to the log and never stops the status update when that server is out of reach. Every ssh2 connection a deployment waits on takes `SSH_KEEPALIVE`.

## Database deployments

`waitForSwarmServiceConvergence` (`packages/server/src/utils/docker/utils.ts`) decides whether a database deployment succeeded. `service.update` clears `UpdateStatus`, so the state it reads belongs to this update, and Swarm sets `updating` about 50 ms later only if a task has to change. A fresh service, an update with nothing to roll out and a scale change never get a state, and until the update starts the running task is the old one, so a missing state counts only after 2 s and only when no running task has another `ForceUpdate`. Task specs cannot be compared with the service spec as a whole: `Runtime` exists only on the service, and a placement change alone rolls nothing out. `rollback_started`, `rollback_completed`, `rollback_paused` and `paused` fail at first sight, because Swarm can replace `rollback_completed` with `completed` seconds later and reports it before the old task is up. `completed` also needs enough running tasks, because `FailureAction: continue` completes with its tasks restarting. Five builders bump `ForceUpdate`, so their every deploy replaces the task and waits at least `UpdateConfig.Monitor`, 5 s by default; `buildLibsql` does not. `getSwarmConvergenceTimeoutMs` scales the limit with the batches, the stop grace period, a health check, Monitor and Delay; the default spec comes to 45 s. Swarm watches a task for `Monitor` only during an update, and a restart loop shows a running task on some polls, so a task counts only once the same task ID has stayed up for `Monitor`. A restart always makes a new task, so the ID tells. Time counts from the panel's first sight of the task, on the panel's clock and only as a difference, plus what the cluster shows from before the service's last change: `UpdatedAt` minus the task's `Status.Timestamp`, used only when the task's `Version.Index` is older than the service's, which rules out a node with a slow clock making a new task look old. So a redeploy that changes nothing still takes 2 s and a `completed` update adds no wait. A fresh service (first deploy, Rebuild, transfer) or a new replica waits for the task and then `Monitor`, 8 to 10 s by default. One that fails once and recovers passes, because a first crash can be transient. One in a restart loop fails as soon as three tasks of one slot (one node for a global service, the key `endedRuns` uses) have failed in this update (failed or rejected, created since the update began, `context canceled` left out), with the count and the last task error, while replicas that each crash once and recover still pass, so a crash loop no longer waits for the limit (45 s by default); a `FailureAction: continue` update whose tasks keep restarting ends the same way. A global service has no replica count, so it needs one settled task for each node that holds a current task, at least one. An update with `Order: start-first` whose task of this update reports `host-mode port already in use` fails at once, because the new task cannot bind the port while the old one holds it and Swarm keeps `updating` until its limit; the message says to use stop-first. A did-not-converge message that carries a `No such image` task error adds that the image exists only where it was built and the service needs a registry. A crash later than `Monitor` goes unseen, as it does for Swarm. Under load a node reports a container's exit to Swarm late (a task that crashed after 3 s stayed `running` for 33 s with the host's disks and CPUs busy), so before it reports success the wait asks the engine of the node it connects to whether the container of each settled task there still runs; a task whose container stopped no longer counts, and the deployment fails at the limit unless Swarm replaces it with one that stays up. Tasks on other nodes go by what Swarm says, as does any task whose container the engine cannot read. A read that fails or gets no answer in 30 s is tried again until the limit, because the update goes on without the panel. `SSH_KEEPALIVE` sees a dead network, not a daemon that took the request and stays silent, and such a read used to hold the deployment's slot in the queue for good. The limit is checked between reads, so a silent daemon can overrun it by up to one read. `swarm-convergence.real.test.ts` and `swarm-convergence-failures.real.test.ts`, with their shared fixtures in `swarm-convergence-real.ts`, run this on real Docker.

## Deployment logs

A deployment's log stays where it was written. Reads and single removals find that place through `getDeploymentLogServerId` (`packages/server/src/utils/deployments/log-server.ts`): the row's build server, otherwise the owning service's server, otherwise the panel. `deployment.serverId` is the exception: it marks a server's setup or hardening run, whose log the panel keeps on its own disk, so nothing connects to that server for it and `getAccessibleServerIds` is the only organization check on reading it. Deleting an application cascades to its deployment rows before `removeDeployments` runs, so past build servers come from the rows loaded with the application. `removeDeployment` keeps the row when the log could not be removed, so the removal can be repeated. The rotation of old deployments drops the row anyway and opens one connection per server, so a dead server neither stops a new deployment nor delays later ones again.

## libSQL replicas

The image comes from the Docker Image field like the other database types: `buildLibsql` sets `libsql.dockerImage` in the spec and `deployLibsql` pulls the same value, both falling back to `LIBSQL_DEFAULT_IMAGE` (`db/schema/libsql.ts`, also the schema default) when it is empty. The Advanced tab shows no Arguments field for libSQL, because the table has no `args` column and `libsql.update` would drop it, and Deploy, Reload and Stop show only with `deployment.create`, as on the other database pages.

`buildLibsql` runs its own command through `/bin/sh -c` in place of the image's entrypoint, and only that entrypoint turns `SQLD_PRIMARY_URL` into `--primary-grpc-url`. `sqld` itself reads `SQLD_PRIMARY_GRPC_URL`, so the panel sets that in Env: the free-text URL stays out of the shell, and a custom `sqld` command replicates too, with its own `--primary-grpc-url` taking precedence. `SQLD_PRIMARY_URL` stays for custom commands that refer to it. `sqld` refuses `--grpc-listen-addr` together with a primary URL, so a replica's command has none, and `buildLibsql` rejects a custom command that has it: Swarm would roll that update back while `waitForSwarmServiceConvergence` had already reported success. The URL takes the primary's gRPC port, 5001. With a wrong host or port the replica keeps running, its requests hang, and its log says `error connecting to primary`. A URL without a scheme makes `sqld` panic on every request while it stays up. `getLibsqlPrimaryUrlProblem` (`libsql-primary-url.ts`, free of server-only modules) rejects it and an empty URL, for `buildLibsql` and for the replica's form.

The form is `ShowLibsqlPrimaryUrl`, and it saves through `libsql.update`, so its permission check is that procedure's. A saved URL reaches the node on the next deploy; Reload keeps the old spec. The URL can hold a password, so `redactDatabaseServiceSecretsFor` hides that part on every read, and the host stays readable. A URL that comes back as shown keeps the stored password. An edited one is saved as sent, placeholder included, so a stored password never travels to a host the caller picked, for the reason in `assertStoredSecretTargetUnchanged`. `apiUpdateLibsql` redefines `enableNamespaces` and `dockerImage` without defaults, because `.partial()` keeps a zod default: every update used to turn namespaces off for the next deploy. Nothing in the panel turns them back on after creation, only the same API.

A command of `""` or only spaces means no override, as null does, so it runs the default command. The custom command form saves `""` whenever it is saved with an empty field, even if only the image changed. Without namespaces `""` used to run the image's entrypoint, which opens no admin port and runs `sqld` as the user `sqld`; with them, `/bin/sh -c " --enable-namespaces"` exited with 127. A service that ran the entrypoint moves to the default command on its next deploy and keeps its data, and a replica keeps replicating with nothing set aside, but `SQLD_DB_PATH` and the `SQLD_*_LISTEN_ADDR` names in its env lose to the default command's flags.

Nodes pick a namespace by the first label of `Host`. A replica needs `--enable-namespaces` to serve named namespaces; without it, it follows only the primary's default one.

Port 5001 serves the whole database, for reading and writing, to any `sqld` that connects as a replica: the password guards only port 8080. So it takes TLS with client certificates. Each organization has one authority (`libsql_grpc_ca`, key in `encryptedText`), made on its first libSQL deployment by `getLibsqlGrpcCa`, and every deployment issues the node a new certificate from it (`libsql-grpc-tls.ts`), which serves a primary as its server certificate and a replica as its client one. `sqld` takes these files only as flags, so they reach the container base64-encoded in `DOKPLOY_GRPC_*` and `LIBSQL_GRPC_TLS_SETUP` writes them to `/tmp/dokploy-grpc` before any command, a custom one included. A replica checks its primary's certificate for the name `sqld` whatever host it dials, so the certificate carries that name and a panel address, an IP or a published port all work. A replica dials `https://` even when its URL says `http://`, so URLs saved before still work. A custom primary command that listens for gRPC without `--grpc-tls`, or a replica's without `--primary-grpc-tls`, is refused, with the flags in the message. A node of another panel or organization cannot connect, and a primary deployed before this keeps taking any node until its next deploy; a replica of it then has to be deployed again too. The cards show the gRPC address without credentials. `libsql-replica.real.test.ts` checks that a node without a certificate, or with one of another authority, reads nothing.

`sqld` connects to the primary on the first request, not at start, and if it finds data without `client_wal_index` it overwrites that with the primary's, with no warning. Replicas used to run as primaries of their own, so the default command moves such an `iku.db` to `iku.db.before-replica-<unix time>` once, in the same volume, and nothing deletes the copy. A custom command gets no such step. `--db-path` stays `iku.db` because the panel's backup form fixes that name. `libsql-replica.real.test.ts` runs all of this on real Docker; after a new image, it is what shows whether that file layout still holds.

## Redis start

`buildRedis` starts a database with `REDIS_START_SCRIPT`, which reads the password from `DOKPLOY_DB_PASSWORD` in Env, so the shell never parses it. `REDIS_PASSWORD` stays in Env for the container, but the service env can set that name and dotenv changes some values, so nothing starts from it. `exec` makes `redis-server` PID 1: with `/bin/sh -c` alone, dash in the Debian image stays PID 1 and never passes SIGTERM on, so a stop ends in SIGKILL with no final save. `command: ""` and `args: []` are what the custom command form saves when left empty, and they count as no override. An empty password stops the start, because Redis takes it as no password. Redis 6 reads a password that starts with `--` as an option name; 7 and up do not. `redis-password.real.test.ts` runs this on real Docker, including the old command as the starting point.

The panel's password change (`changeRedisPassword`, `utils/databases/redis-password.ts`) writes `DOKPLOY_DB_PASSWORD` and `REDIS_PASSWORD` into the service spec, because Swarm restarts a task from the spec and `CONFIG SET requirepass` lives in memory. Swarm cannot change a spec without replacing the task, so every change is a restart: clients drop for about half a second on a small database, Redis makes its final save on SIGTERM, and old connections end, which `CONFIG SET` left alive. Nothing else in the spec moves, so env edits and an image that wait for a deploy still wait. Nothing goes to Redis first, so a failed update leaves everything as it was and the row's transaction rolls back. The mutation waits for `UpdateStatus` and fails only on `rollback_*`, since Swarm then went back to the old spec; past the 90 s deadline the new spec stands, so the row follows it. `redis-cli` exits with 0 when Redis refuses, so only the reply counts. A database still on the old command gets `SAVE` first, because its stop ends in SIGKILL: the row's password, then the one in the old command's text. Writes in the 10 s between that save and the kill are lost, once. A custom command decides what a restart brings back, and restarting could undo the change at once, so it gets only `CONFIG SET`, and the dialog says so. A stopped database changes only in the spec and needs no container.

## Taken from upstream, not in use

The Server Security dialog (`routers/server-security.ts`, `services/server-security.ts`) runs root commands over SSH on remote servers, and its writes need `server:create`; the fork's Apply hardening button lives in that dialog now. `banFail2banIp` refuses the panel's address only when `webServerSettings.serverIp` is set and matches, so a panel that reaches the server from another address can still ban itself. `togglePanelPort` publishes or removes port 3000 on the panel's service, and the fork's update path has not been checked against a removed port. PostHog code stays, but `getPostHogKey` returns null unless `IS_CLOUD`, so a self-hosted panel contacts nobody. Upstream's Bitbucket watch paths are unreachable: `isProviderDeployWebhookAuthenticated` refuses every Bitbucket webhook, because Bitbucket has no signature the panel checks, so upstream's `bitbucket-watch-paths.test.ts` is left out. Upstream's 3 s task loop in `mechanizeDockerContainer` is left out too, because `waitForApplicationRollout` covers it with a limit on each read.

Deploy webhooks (`pages/api/deploy/[refreshToken].ts`, `compose/[refreshToken].ts`) turn Next's body parser off and read the body themselves (`readDeployWebhookBody`), so a signature is checked against the bytes the provider signed: Gitea marshals its JSON in Go, and `JSON.stringify` of the parsed body is a different text. A request with a provider event header must carry that provider's proof: GitHub `X-Hub-Signature-256` with the GitHub App's webhook secret, GitLab `X-Gitlab-Token` equal to the provider's Deploy Webhook Secret (`webhookSecret`; the OAuth `secret` is accepted only while no webhook secret is set, as before), Gitea `X-Gitea-Signature` (HMAC-SHA256 hex of the raw body) with the new Deploy Webhook Secret of the Gitea provider (`gitea.webhook_secret`, migration 0217, set in the provider dialog and the Secret field of the Gitea webhook). Applications and composes of source type Custom Git have no provider row and so no secret to check, and Bitbucket and Soft Serve have no check: their provider-header requests stay refused with 401, which was a deliberate part of the hardening (a token holder could otherwise forge a branch with headers). Gitea and Forgejo also send `X-GitHub-Event` and `X-Hub-Signature-256` for GitHub compatibility, so `getProviderByHeader` checks GitHub's header last; with it first, every real Gitea push was read as GitHub and refused with 401 (found with a real Gitea 1.24 on 2026-11-08). A request with no provider header skips the check as before, and for Git sources it ends in 301 "Branch Not Match: the request has no Git provider event header", since the branch is read from the header. `__test__/deploy/gitea-webhook-signature.test.ts` covers it.

`application.one` and `compose.one` return `refreshToken` as `__DOKPLOY_REDACTED_SECRET__`, so the Deployments tab showed and copied `/api/deploy/__DOKPLOY_REDACTED_SECRET__` (found 2026-11-08). It now shows the URL with dots and, on the first click (copy), calls `application.revealWebhookToken` or `compose.revealWebhookToken`: browser session only (`api-key-output-guard.ts` refuses API keys), the `deployment: create` permission on that service, and a `reveal` audit entry. Regenerating the token forgets the answer. `__test__/components/webhook-url-reveal.test.ts` guards it.

## Removing projects and environments

`project.remove` and `environment.remove` refuse with `CONFLICT` while they hold a service, through `environmentHasServices` (`utils/environments/has-services.ts`). The rows cascade, but nothing stops the Swarm services or removes their files, so the service would keep running and the panel could no longer see or remove it. The form already disables its button in that case, so only API clients meet the error.

## Service updates

The application, database and rollback builders write a service through `createOrUpdateSwarmService` (`utils/docker/swarm-service.ts`). Only a 404 leads to a create. Each of them used to create on any error, so a refused update reached the user as `name conflicts`. Each call has 30 s, and one that gets no answer is not repeated, because the daemon may still apply it. The `abortSignal` can go into the options: `docker-modem` removes it before it builds the query and the body. `__test__/docker/swarm-service.test.ts` runs against a real HTTP server through dockerode, and fails if an upstream merge brings `docker.createService(` back to these eight files. `redis-password.ts`, the setup code and the terminal or log reads have calls of their own without this limit.

## Application deployments

All four deploy paths in `services/application.ts` end in `rollOutApplication`: `mechanizeDockerContainer`, then `waitForApplicationRollout` (`utils/builders/index.ts`), which is `waitForSwarmServiceConvergence` with an option the databases do not use. The wait reads the service on `application.serverId`, while the log lines stay on the server that built the image. A pull on the node that runs the task and a HEALTHCHECK of the image itself show in no spec, so `quietStartAllowanceMs` gives a task that reports no error 10 more minutes per batch; a fixed 45 s would fail healthy deployments. As soon as a task carries an error (a crash, `no suitable node`), the limit of the spec, 45 s by default, runs from that moment, because Swarm restarts a fresh service's task forever and leaves a stuck update in `updating`, and only this ends them. A start-first update of a service with a host-mode port cannot start on one node: Swarm stays in `updating` with `host-mode port already in use`, so this now fails instead of reporting success. Job modes never get here, because Docker refuses a job with `UpdateConfig` and `generateConfigContainer` always sends one. The panel's Rollback (`services/rollbacks.ts`) waits the same way and sets the application to `done` or `error`, because the status of the deployment it undid stayed otherwise. So does `reload` (`reloadApplication` in `services/application.ts`, which the router calls): `running`, a new task by `ForceUpdate`, the wait, then `done`, or `error` with the reason in the mutation's message. The database `reload` procedures are another code path and still do not wait. `application-rollout.real.test.ts` runs this on real Docker.

## Stack deployments

`deployCompose` and `rebuildCompose` end a stack in `rollOutCompose`, because `docker stack deploy` exits 0 after it wrote the specs and `--detach=false` exits 0 with `converged` after a rollback. `waitForStackRollout` (`utils/docker/stack-rollout.ts`) finds the services through `com.docker.stack.namespace` and runs `waitForSwarmServiceConvergence` on each, with the allowance of an application. It reports every service that failed, and keeps four waits open at once, because over SSH every read is a connection and `sshd` starts dropping new ones at 10 in progress. A redeploy that changes nothing takes about 2 s per four services. A job has no rollout and is not waited for, so a failed job goes unseen. Compose files leave the failure action at Swarm's default, `pause`, so a broken update ends `paused` with its task restarting: this used to read as success too. The `docker-compose` type has no Swarm and is checked by its containers, below.

Migrations in a stack are often services with `restart_policy: { condition: none }` or `on-failure`. A task that ended leaves `DesiredState: shutdown`, so the wait goes by the newest task of each slot (`endedRuns`): `complete` counts, and `failed` or `rejected` fails at once, because nothing will run it again. Swarm does not start a task again for an unchanged spec, so a failed one fails every deploy until its spec changes. Swarm also counts any task that ends during `Monitor` against the update, exit 0 included: a short task updated this way ends in `paused`, which the wait accepts only if every slot's newest task is `complete` and from this update. With `failure_action: rollback` the same task really rolls back and re-runs the old spec, so that stays an error. `stack-rollout.real.test.ts` runs all of this on real Docker.

## Compose deployments

`docker compose up -d` exits 0 once it has started the containers, also when one of them crashes right away, keeps restarting or fails its health check, so `deployCompose` and `rebuildCompose` end the `docker-compose` type in `waitForComposeContainers` (`utils/docker/compose-containers.ts`). It reads every container with `com.docker.compose.project=<appName>` on the compose's server, without `docker compose run` one-offs. A running container counts once it has been up for 10 s, the time after which Docker's restart manager also resets its delay, and once its health check, if it has one, says `healthy`; `unhealthy` fails at first sight. A container that exited with 0 counts, so migrations pass. One that exited with another code fails at once when its restart policy will not start it again (`no`, or `on-failure` with its retries used up). A container that restarts gets 45 s from the first restart the panel sees to stay up, because a service can crash once while its database starts; a restart loop fails then with the last exit code. Docker keeps an old `StartedAt` while a container waits between restarts, so `restarting` counts whatever the start time. Every failed container is reported, with any container seen restarting at that moment, since it is often the cause or the result; the whole wait stops at 10 minutes, for health checks with a long start period.

`up` starts again every stopped container of the services it runs, so a container that ended before this `up` belongs to a service it left out (a profile, or a custom command naming services) and is left alone. Start times come from the daemon's clock and `startedSince` from the panel's, so the offset is measured once through `docker info`, with a margin of 1 s. Containers that this deployment did not change are checked too: one that was already unhealthy or restarting now fails the deployment. A redeploy that changes nothing takes a second or two more, and one that recreates a container at least 10 s more. A crash later than 10 s after the start goes unseen. A read that fails is tried again for 45 s. `compose-containers.real.test.ts` runs this on real Docker.

Compose can keep a running container when only the `content` of an inline config it mounts changed: removing two lines of an XML config left the old container and file on 5.6.1 and 5.7.0, while a one-line edit was seen. So `addDomainToCompose` gives each service of a `docker-compose` file that mounts inline configs the label `com.dokploy.config-hash`, a hash of their contents (`applyInlineConfigHashLabels`); a changed label always recreates the container, and an unchanged one leaves it alone. Variables in the content count as written, and configs from files or the environment are not covered. `compose-inline-config.real.test.ts` shows both the miss and the label on real Docker.

## Mongo replica sets

`replicaSets: true` replaces the image entrypoint with the script in `packages/server/src/utils/databases/mongo.ts`, so `MONGO_INITDB_ROOT_*` do nothing there and the script itself runs `mongod --auth --keyFile`. The key file is generated at `/data/db/.dokploy-keyfile`, in the data volume, so it goes with the data through a volume backup or a rebuild. Credentials reach the script through `DOKPLOY_DB_USER` and `DOKPLOY_DB_PASSWORD` in Env, never through its text. Data without a key file gets one more start without access control on the next deploy, which makes the stored user and password valid, and then restarts with it; nothing changes for a running database until that deploy. `mongo-replica-set-auth.real.test.ts` runs all of this on real Docker, including the old script as the starting point. It uses `mongo:7`: `mongod` 8 refuses to start on kernels from 6.19 up to 7.0.13 (SERVER-121912), and GitHub-hosted runners have 7.0.0.

The connection strings the panel shows come from `apps/dokploy/lib/mongo-connection-url.ts`. The external one always carries `directConnection=true`: a replica set names its member `<appName>:27017`, which resolves only inside the Docker network, so a driver outside that follows discovery cannot connect. The internal one leaves discovery on for a replica set. `mongosh` adds `directConnection=true` to a one-host URL that does not set it, so a check through `mongosh` sees what a driver does only with an explicit `directConnection=false`.

## Mongo tool arguments

`getMongoBackupCommand`, `getMongoRestoreCommand` and `buildMongoPasswordChangeCommand` pass `--username=<user>` and `--password="$DOKPLOY_DB_PASSWORD"`, with the password in `docker exec -e`. The password validator allows a leading `-`, and the `-p <value>` form fails on it however well the shell quotes it: `mongodump` and `mongorestore` refuse `-x` and `--port` before connecting, and `mongosh` also refuses a lone `-`. The text of a failed command reaches the UI, and an env assignment is what `redactSensitiveText` masks whole. `__test__/backups/mongo-password-argument.test.ts` fails if an upstream merge puts the old form back. `mongodump -d <name>` exits 0 with an empty 137-byte archive for a database that does not exist (checked on mongo:7), so `getMongoBackupCommand` first asks `mongosh` for the database names (the name travels in `DOKPLOY_DB_NAME`) and fails with `Database <name> does not exist`, before any dump; an image without `mongosh` skips the check. `pg_dump`, `mysqldump` and `mariadb-dump` already exit non-zero for a missing database. `__test__/backups/mongo-backup-missing-database.test.ts` covers it.

## Database connection strings

The strings the panel shows for Postgres, MySQL, MariaDB, Redis and libSQL come from `apps/dokploy/lib/database-connection-url.ts`, and Mongo's builders use its `encodeCredentials` and `formatUrlHost`. The user, the password and the database name are percent-encoded, because `DATABASE_PASSWORD_REGEX` allows `@ : ? # %` and no validator limits the name. A host with a colon gets brackets, because `getPublicIpWithFallback` falls back to IPv6 and `server.ipAddress` accepts any text. Two clients fail on such a string for reasons of their own: `@libsql/client` refuses any URL with credentials, and `node-redis` looks up the address with its brackets.

`*.one` returns the passwords as `__DOKPLOY_REDACTED_SECRET__`, so these strings used to carry the placeholder, and the copy button gave a string that could not connect. The credentials cards build them through `useDatabaseCredentials` (`hooks/use-database-credentials.ts`): the first eye or copy click on a value that holds the placeholder calls `<type>.revealCredentials`, and every string of the card is built again from the answer. That procedure has the check of `revealEnvironment`, the service's `envVars` read permission, because a database's env shows as much, and `api-key-output-guard.ts` refuses it to API keys. A password change forgets the answer. `__test__/components/database-credentials-reveal.test.ts` fails if a card shows a string built from `data` again.

## Sidebar while permissions load

`components/layouts/side.tsx` shows a link only where it will stay. Until `user.get`, `user.getPermissions` and `settings.isCloud` have answered, the menu shows the links above the first gated item (Home and Projects) and `SidebarMenuSkeleton` rows for the rest, so a link that appears later cannot push another one under the pointer and no link shows that the user may not use. A failed request ends the wait after React Query's retries, about 7 s, and then only the links without a gate remain. An item with `isEnabled` placed above Projects would hold that link back too. The header's spinner has the height of the organization selector (`h-12`, `h-20` when collapsed), and the footer keeps the version labels until the versions arrive. The user menu's email line has a fixed `h-4`, so "Account" does not move when `user.get` answers. White-label needs a valid license, so the footer text holds one `min-h-4` line while `whitelabeling.get` loads only when `licenseKey.haveValidLicenseKey` is already true; an unlicensed panel reserves nothing. ## Server runtime

The image starts the panel's server, its migration and `wait-for-postgres` on Bun, the server with `--smol` (`CMD` in `Dockerfile`). On the same panel Bun answered API calls 7-24% and pages 14-19% faster than Node 26, started in 2.8 s instead of 6.2 s and peaked at about half the memory under load, while holding 50-70 MB more at rest. Bun reads `/app/.env` by itself, which `node -r dotenv/config` did before. Node stays in the image, so a service command can run the same build on Node; the comment above `CMD` has it.

Bun also answers an import of five packages with built-in modules of its own: `undici`, `ws`, `buffer`, `string_decoder` and `node-fetch` (on 2026-11-08, with Bun 1.4.4, from `require.resolve` over every package in the image). Bun's `undici` has an `Agent` without `close()`, and its `fetch`, like Bun's global one, ignores `dispatcher`. So the address pin of `fetchWithPublicEgress` (`utils/url/network.ts`, used when private networks are off, as in the cloud), the private-address check of `providerFetch` (`services/logs-and-metrics/provider-fetch.ts`) and the Telegram sender's timeouts were skipped, and every `close()` threw: the first Bun build ran on the panel for 90 s before it was rolled back. These three import `Agent` and `fetch` from `utils/undici.ts`, which loads the package by its file (`undici/index.js`), and send through that `fetch`, since Node's and Bun's own `fetch` reject or ignore its Agent. A new import of `"undici"` anywhere in the server repeats the problem, and tests mock `@dokploy/server/utils/undici`, not `undici`. `__test__/server/undici-bun.test.ts` runs the module in a Bun process. Bun's `ws` refused a foreign `Origin` through `verifyClient` and closed an oversized message with 1009, as `ws` does on Node; `node-fetch` comes in only through `cross-fetch`, and becomes Bun's `fetch`.

Three checks keep the server on Bun. `__test__/server/bun-runtime.test.ts` fails if the image's `CMD` or the `start` script runs the server with anything but `bun`, and if Bun answers any package of the workspace with a built-in module beyond the ones checked so far (`undici`, `ws`, `buffer`, `string_decoder`, `node-fetch`): a new one, after a Bun update or a new dependency, gets the check `undici` got before the list there grows. `undici-bun.test.ts` runs `utils/undici.ts` in a Bun process and fails on any other import of `"undici"` by its name in the server. `main-image-smoke` starts the built image with Postgres and a swarm, and fails unless the server answers, its process is `bun`, and the image's `utils/undici.js` pins a request to the address its lookup gives. The owner wants the panel on Bun: a problem under Bun is fixed on Bun, and Node stays in the image only for an emergency.

Under Bun, node-pty's child gets SIGHUP right after its first output: the container terminal and logs of the panel's own server printed one line and stopped. `spawnPty` (`server/wss/pty.ts`) takes the PTY from `Bun.spawn(cmd, { terminal })` when `globalThis.Bun` exists and imports node-pty only on Node, so the tests, which run on Node and mock `node-pty`, keep their mocks. Remote servers get their PTY from `ssh2` and are not affected. `__test__/wss/pty-bun.test.ts` runs the Bun branch in a Bun process: two lines with a pause, multi-byte text split across reads, input, resize, the exit code and kill. `main-image-smoke` runs a command through Bun's PTY in the built image.

Bun answers `ENOTFOUND` to `resolve4`/`resolve6` for a name that exists but has no address record, where Node answers `ENODATA` (found 2026-11-08), so `mapDnsStatus` alone would show "nxdomain" for such a domain on the panel. `resolveDomainRecords` (`utils/domain-overview/dns-status.ts`) therefore asks TXT, MX, NS, SOA, CNAME and CAA when an address lookup says `ENOTFOUND`, and a name that answers any of them (or says `ENODATA` to one) turns the address codes into `ENODATA`. A name with no record of those types at all still reads as nxdomain. `__test__/server/dns-status-runtime.test.ts` asks a fake UDP resolver (`fixtures/fake-dns.ts`) from Node and from a Bun process.

## Docker API of remote servers

## Websocket handlers

Every server in `apps/dokploy/server/wss/` registers through `onWebSocketConnection` (`onJsonWebSocketConnection` for a client that parses every message as JSON) and reads the path with `readUpgradePathname`, both in `server/wss/connection.ts`. The fork has no process-level listeners of its own: only Next's, installed by `app.prepare()`, keep the panel alive after an exception from a handler, an `upgrade` listener or the HTTP listener in `server.ts`, and they only log it, leaving the socket open with nothing on it. The wrapper logs the failure, tells the client and closes with 1011. Its text is generic because the session check runs first, so the error could reach a client that has not signed in. It also adds the `error` listener, since `ws` emits a malformed frame as `error` and an emitter with no listener throws. `ws.close()` throws on a reason over 123 bytes, so a reason built from an error goes through `toCloseReason`.

The server terminal (`server/wss/terminal.ts`) ends the ssh2 connection, not only the shell channel, on every way out: socket close, socket error, a failed shell, an ssh error. Ending the channel alone left the connection, the remote shell and anything typed in it running for good, one per open, and the panel kept their output. The sshd hangs the shell up when its connection drops, so no hangup command is needed (the container terminal needs one, since `docker exec` outlives its ssh channel). `conn.destroy()` follows after 3 s for a connection still being made or on a dead network. `stopWhenClientIsSilent` (`connection.ts`) pings every 30 s and terminates a socket that left no pong, so a client that vanished without a close frame is released too, and the connection takes `SSH_KEEPALIVE`. `__test__/wss/terminal-ssh-release.test.ts` counts the connections a real in-process ssh2 server still holds, and its Bun twin runs the same 20 cycles in a Bun process, or against a real sshd with `SSH_HOST`, `SSH_PORT`, `SSH_KEY_FILE` and `HOLD_MS` set.

The container terminal (`docker-container-terminal.ts`) hangs up its shell by scanning the container for the session's marker (`getTerminalHangupArgs`), and runs that scan not once but at close, then after 0.5, 2 and 5 s (`runHangupScans`, `server/wss/hangup-scans.ts`). `docker exec` creates the shell on the daemon's own time, so on a slow daemon it can start after a one-shot scan has finished and nothing would end it. The scans never overlap, stop at the first one that cannot run (a dead SSH connection), use unref'd timers, and on a remote server share the one SSH connection, which ends after the last scan (30 s at the latest). The marker keeps every scan on that session's own process, never another user's shell. `__test__/wss/hangup-scans.test.ts` uses fake timers, `hangup-scans-bun.test.ts` runs real child processes in a Bun process, and `docker-container-terminal-hangup.test.ts` covers a late shell on a local and a remote session.

`closeUnknownUpgradePaths`, the last listener `server.ts` adds, answers 404 and closes an upgrade to a path no server handles. Nothing reads such a socket and Node has dropped its timeouts by then, so it would stay in `CLOSE_WAIT` until a restart, even after the client left. Next closes only paths that match a page and leaves the rest on purpose, since an application's own server may listen there. The paths have no list to keep in step: the two helpers record `wss.options.path` when a server registers, so a server that was not set up, like the stats one in the cloud, counts as unknown. In dev everything under `/_next/` stays open for Next's own listener. Its hot reload socket is `/_next/hmr` in Next 16.4, so the `/_next/webpack-hmr` check each listener keeps from upstream matches nothing. Node passes any `Upgrade` header to these listeners, so `curl --http2` over plain HTTP gets this 404 too. `__test__/wss/handler-errors.test.ts` fails if an upstream merge brings back a plain `wss.on("connection")` or `new URL` in an `upgrade` listener, or adds a server without a `path`, outside `server/wss/` or missing from the list its socket tests run on.

## Scheduled jobs

Every async callback given to node-schedule's `scheduleJob` goes through `guardScheduledRun` (`utils/crons/guard.ts`), which logs the error once (job id, redacted message) and does not rethrow. node-schedule drops the promise of an async callback, so an error that left a job used to end as an `unhandledRejection`, kept from killing the panel only by Next's process listeners: every failing scheduled backup logged one (3 on Node, 24 on Bun in one test run). ## Notification secrets

The notification API returns `__DOKPLOY_REDACTED_SECRET__` in place of every secret field (`notificationSecretFields` in `utils/notifications/security.ts`, plus the values of custom headers), and an update that sends it back keeps the stored value. Test sends what the form holds, so on a saved channel it used to send the placeholder: Telegram answered 404 and every saved channel failed its Test. The form now passes `notificationId`, and `withStoredNotificationSecrets` (`services/notification.ts`) puts the stored secret in place of the placeholder after the router's `notification:update` check. A stored secret goes only to the target it was saved with, by the same rule as an update (`assertStoredSecretTargetUnchanged`): the SMTP server, port and user, the Gotify or ntfy server, and the custom endpoint for its saved headers.

`NotificationSecretInput` shows each secret as dots with an eye. On a saved value the eye calls `notification.revealSecret`, which answers only the owner and admins in a browser session, refuses API keys (`api-key-output-guard.ts`) and writes a `reveal` audit entry. The 13 secret columns are `encryptedText`, as service env is, so no migration changes the column type; `encryptStoredNotificationSecrets` writes rows saved as plain text once more at panel start. Custom headers are `jsonb` and stay plain. An image from before this change reads the encrypted values as they are, so going back to it needs the database dump taken before the update or the secrets entered again. `__test__/notification/notification-saved-secret-test.test.ts` covers all of this.

Every `update<Provider>Notification` skips a table whose `set` would hold no defined value, because drizzle fails an empty `set` with `No values to set`: an API client that sends only an event flag changes the notifications row and leaves the provider row alone, and one that sends only provider fields leaves the notifications row alone (`updateNotificationRow` and `hasValues` in `services/notification.ts`). A secret kept through its placeholder is `undefined` and counts as no value. `__test__/notification/notification-update-partial.test.ts` covers it.

## Restore failures

`backup.restoreBackupWithLogs` ends a failed restore with a tRPC error after the log lines, so the client leaves its "restoring" state and shows the message. The message and the `Error:` log line come from `formatRestoreError` (`packages/server/src/utils/restore/failure.ts`): the error text plus the tail of the command's stderr (remote errors say only "exit code 1" otherwise), passed through `redactSensitiveText`. `reportRestoreFailure` sends a failure message to the `databaseBackup` channels through `sendDatabaseBackupNotifications` with `operation: "restore"`, which only changes the wording. Restores never send success messages, so the failures-only settings hold. A web-server restore gets the error but no notification.
